# Artifact Policy

## Purpose

Clarify which generated files should be tracked in Git versus regenerated locally—without deleting assessment evidence from the working tree.

## Recommendation Summary

| Path / pattern | Track in Git? | Notes |
|----------------|---------------|--------|
| `output/.gitkeep` | Yes | Keeps directory present |
| `output/**` (runtime artifacts) | **No** (gitignore) | Regenerated by engine runs |
| Assessment evidence copies under `deliverables/` | Optional Yes | Archive curated copies for portfolio/submission |
| `test-results.xml` | No | CI/local JUnit output |
| `src/*.egg-info/` | No | Packaging metadata |
| `__pycache__/`, `.pytest_cache/` | No | Caches |
| `resources/templates/*` | Yes | Source templates |
| `examples/*` | Yes | Operator documentation |
| Screenshots under `screenshots/*.png` | Yes (when real) | Portfolio assets; do not invent |

## Assessment Evidence Guidance

**Do not delete** existing files under `output/` on disk if they represent completed assessment runs.

For Git hygiene:

1. Keep `output/` contents gitignored for day-to-day development.
2. If a durable assessment archive is required, copy selected artifacts into `deliverables/` and document what was copied.
3. Prefer redacting or excluding secrets, session tokens, and environment-specific noise from any tracked archive.

## Rationale

- Runtime recon output is non-deterministic across environments and pollutes diffs.
- Templates, docs, and examples are the source of truth for contributors.
- Portfolio reviewers care about curated evidence samples—not every local re-run.
